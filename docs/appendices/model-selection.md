# 模型选型与对比记录

日期：2026-10-29。阶段：本机最小原型。结论只适用于本轮任务、语料和运行配置，不代表正式诊断能力或现场验证结论。

## 1. 选型方法

先选可运行基线 → 固定任务与输入 → 保存原始结果与失败 → 在相同设置下对比候选 → 结合正确性、约束遵守、时延和资源确定当前版本默认值 → 扩大测试后再复核。

预置模型不是因为“更大/更新”就默认最好。第一轮优先复用本机已有权重，避免下载和微调；该阶段没有配置或调用云端模型。之后用户指定通用模型采用DeepSeek API，接入与新默认配置见第7节，Embedding仍在本机运行。

## 2. 本机环境与初选

- CPU：Intel i5-12500H；内存约16GB；GPU：RTX3050 Laptop 4GB。
- Ollama 实际模型摘要、量化和能力在 `research/ollama-model-metadata.jsonl`；精确 digest 另保存于每次实验 JSON，模型标签可变，不只记录名称。
- Agent 初选 `qwen3.5:2b`，本机为 Q8_0、具备工具调用能力；职责是理解问题、选工具与草稿整理。对照 `qwen3.5:0.8b` 同为 Q8_0，考察更低资源/延迟能否满足相同约束。
- Embedding 初选 `bge-m3:567m`，本机为 F16、多语言且已存在；对照 `qwen3-embedding:0.6b`，本机为 Q8_0。两者本轮均返回1024维向量。
- 原先建议的 bge-small-zh-v1.5 暂不下载：发现本地已有上述权重后，优先验证现成配置。它仍是后续低资源候选，未测试不能写成输赢结论。
- 首发不微调、不接独立轴承分类模型，也不加 reranker。先用确定性信号工具验证 Agent；分类模型后续作为独立工具评测。

Embedding 按 CPU、8线程请求，Agent 由 Ollama 自动安排设备；运行中一次 `/api/ps` 显示2B约1.92GB显存分配。该快照不是峰值内存测量，也不代表整个服务只占这些内存。

## 3. Embedding 开发对比：已实测

### 协议

- 10张开发自编中文知识卡片、30条开发自标注问题；不是厂家手册或专家金标，不是独立留出集。
- 文本短于模型上下文，禁止静默截断；文档不加查询指令。BGE-M3查询用原问题，Qwen查询加其模型约定的任务指令。
- 向量归一化后用余弦排序，不添加 reranker、额外关键词加权或不同切块。
- 每模型重新编码同一语料；1次预热后逐条查询，单查询batch=1、每题1次。模型顺序固定BGE后Qwen；记录语料/问题hash、模型digest、索引时间与每题结果。
- F16与Q8量化不同，本轮比较的是实际部署配置，而不是在同精度下隔离模型架构优劣。只有30题且无重复时延测量，数字不作统计显著性证明。

| 配置 | Top-1 | Recall@5 | 预热后查询墙钟P95 |
| --- | --- | --- | --- |
| BGE-M3 567M F16 CPU | 28/30（93.33%） | 30/30 | 约0.117秒 |
| Qwen3-Embedding 0.6B Q8_0 CPU | 25/30（83.33%） | 30/30 | 约0.252秒 |

当前保留 BGE-M3 检索基线：在本次中文开发题上Top-1更高、实际CPU查询更快，且无需额外下载。没有因此认定它在所有知识库上优于Qwen。

原始记录：[retrieval-dev-results.json](../../experiments/retrieval-dev-results.json)。问题与卡片在 `data/evaluation/`、`data/knowledge/`，都是开发资产。

## 4. Agent 开发对比

### 固定任务与设置

两个模型均使用：真实Ollama调用、关闭thinking、temperature=0、seed=42、4096上下文、每次最多512输出token、最多2轮工具决策、同一BGE-M3知识检索和同一正弦信号。

案例：A01只看RMS与主频；A02缺转速时先检查轴承必要条件；A03先检索包络方法。每模型每案例1次，时延含加载。只有3题不能算正式 Agent 成功率或P95，也不能比较正式轴承分类准确率。

评价分别记录：期望工具覆盖、原始工具路径、结构/引用校验首过、修正次数、最终校验、实际输出、模型用量与执行时间。格式/引用通过不能证明文本语义正确；需保留人工检查发现。

### 迭代历史

1. 首轮仅JSON模式：2B三个草稿中1个通过结构/引用检查；0.8B三个均未通过，多次复制输入结构并在512token处截断。工具路由仍有可用表现。保留 [首轮原始结果](../../experiments/agent-dev-results-round1.json)。
2. 第二轮采用原生JSON schema、动态证据ID枚举和来源约束：两模型均2/3草稿通过当前校验。2B有未知转速状态错误；0.8B有将提供参数说成测量事实的问题，均被阻断。保留 [第二轮结果](../../experiments/agent-dev-results-round2.json)。
3. 第三轮在相同schema策略上为两模型统一增加最多1次校验反馈修正；首过与修正后结果分别记录，不能把修正后的通过冒充模型一次成功。结果见 [当前实验记录](../../experiments/agent-dev-results.json)。本轮修正没有挽救剩余失败，保留原始失败及修正输出。

| 第三轮配置 | 期望工具覆盖 | 草稿校验首过 / 修正后 | 三例实际墙钟耗时 |
| --- | --- | --- | --- |
| Qwen3.5 2B Q8_0 | 3/3 | 2/3 → 2/3 | 21.33、22.64、26.69秒 |
| Qwen3.5 0.8B Q8_0 | 3/3 | 2/3 → 2/3 | 9.25、4.25、5.34秒 |

2B对A03仅请求知识检索，0.8B又额外请求频谱；期望工具“覆盖”不等于路径最优。2B在A02持续给错信息缺失状态被阻断；0.8B在A03持续混淆转速来源被阻断。小模型更快，但上述3例无法证明质量相当或哪个可作为正式诊断模型。

人工检查还发现：第二轮2B即使格式通过，仍在A01中把普通频谱观察扩展为“未发现转速相关故障频率”等未经专门工具验证的陈述。因此当前所有结果仅为待人工检查草稿，不能因自动校验通过就宣布可靠诊断。

### 本地对比结束时的决策（通用模型默认项后由第7节更新）

- **检索：保留 BGE-M3 567M 作为本机原型默认配置**，依据是本轮开发题的准确性与延迟；正式知识库测试后再决定是否替换。
- **Agent：保留 Qwen3.5 2B 作为可运行开发基线，0.8B保留可切换对照**。2B的初选理由是已有权重、工具能力和本机可承载；本次测试没有证明它整体优于0.8B，不能把暂留写成胜出结论。
- **正式诊断模型尚未最终确定**：两个候选都有约束/语义失败，需改进证据输出契约、扩大评测，并考虑更强的本地/API候选。当前不微调来掩盖工具或输出契约问题。
- 原型不发布确定性故障结论，不开放工单。自动检查通过仍需人工检查自然语言支持性；不存在“JSON过了所以可工厂试用”的结论。

### 原型端到端核对

- 16项数值、API及Agent校验单元测试通过；依赖一致性检查通过。
- 浏览器真实上传合成CSV，后端返回200，RMS约0.70711、峰值1、Pearson峭度1.5，保存后刷新可读取。
- 浏览器实际调用2B，模型请求了 `inspect_spectrum` 并生成结构合格草稿；另验证BGE-M3知识检索可在页面返回卡片。
- 浏览器该次输出经修正后只强调转速来源，未完整回答用户的RMS问题。这是回答相关性不足，不记为语义验收通过；数值仍由独立指标卡提供。
- 当前自然语言只允许作为原型草稿展示，正式版需把回答相关性、未检查频率的断言、错误来源和证据支持性纳入完整测试。

## 5. 正式选型前还需完成

1. 检索：补充有来源的知识、同义表达、英文术语、无答案及相近干扰；用与调参分离的查询集，检验Recall、MRR、引用和拒答。
2. Agent：至少30个可回答与30个应拒答案例，覆盖参数矛盾、工具失败、注入、无证据、重复调用与长上下文；每例重复运行并区分冷启动/预热。
3. 先锁定评价标准和数据划分，再对比模型；按相同的任务预算、工具和输出契约评测。prompt或约束改变后，对所有候选重测并保留之前失败。
4. 同时检查原始内容的语义支持性、工具选择必要性、数值来源与人工复核工作量，不只看JSON成功率。
5. 同步测量应用/模型RAM与VRAM峰值、持续运行、成本及上下文；本轮没有峰值测量，不补造数据。
6. 正式版本可继续比较可用的API模型或更合适的本地量化模型；是否外发必须有明确配置。本轮未测试云端候选，不提前排名。

选型记录最终要能回答：任务需要什么能力、有哪些候选、为什么先选基线、测试如何公平、失败是什么、为什么当前版本保留或替换，以及在哪些条件下重新评估。

## 7. 通用模型切换到 DeepSeek API

用户明确指定采用 DeepSeek API 后，默认通用模型改为 `deepseek/deepseek-flash`。账户 `/models` 返回可用 Flash（显示名DeepSeek-V4.1-Flash）和 Pro；采用官方当前推荐的Flash作为开发基线，实际服务返回model字段和响应ID逐次记录，不声称供应商别名永远对应同一权重。

选择理由：此前本地小模型已出现内容与约束失败；API模式无需占用本机有限显存，继续保留工具调用与JSON输出能力；开发先用Flash跑通，Pro或其他供应商的正式优劣仍需固定协议比较。本次没有测试Pro，也没有用3个案例宣称Flash整体胜出。

### 接入与密钥边界

- 密钥只保存在被忽略的本地 `backend/.env`（前后端分离前位于根目录），示例文件无真实密钥。客户端不读取/发送Key，API后端不将认证头和供应商错误正文写入结果。
- 外部调用需显式启用。用户指定的当前开发配置已启用；关闭后任务明确报错，不悄悄退回本地模型。
- 发送合成测试问题、采样元数据、必要特征/峰值及开发知识片段；未外发原始CSV和完整波形。真实设备数据以后按正式外发权限要求处理。
- DeepSeek标准接口采用JSON object模式加本地Pydantic/引用校验，不冒称等同于Ollama的原生JSON schema受限解码。
- 工具返回保留原始 `tool_call_id`；多工具请求超过单轮执行预算时逐项给出未执行结果，避免破坏供应商工具会话协议。

### 真实API冒烟结果

| 案例 | 实际工具 | 草稿/约束校验 | 自动执行耗时 |
| --- | --- | --- | --- |
| 仅看RMS与主频 | inspect_spectrum | 通过，给出约0.707 m/s²与128 Hz | 4.35秒 |
| 转速未知，检查轴承诊断条件 | check_bearing_preconditions | 通过，needs_information并列出缺失项 | 4.13秒 |
| 解释包络分析方法 | search_knowledge | 通过，区分知识说明与当前测量 | 7.74秒 |

三例总用量8131 tokens，记录实际供应商usage，不在未知单价时估算费用。额外浏览器端到端调用单独留在运行记录。本轮每次最大输出1024token，与此前本地512token设置不同，因此这些时延和通过数只用于接入验证，不能当作严格控制变量的模型排名。

原始结果：[deepseek-api-smoke.json](../../experiments/deepseek-api-smoke.json)。连接发现：[deepseek-connection.json](../../experiments/deepseek-connection.json)。单位测试增加供应商报错脱敏、外发开关、工具ID及JSON模式适配，累计22项通过；源代码/文档/实验结果的当前密钥泄漏扫描未发现匹配。

**当前开发组合：DeepSeek Flash API＋本地BGE-M3，不做微调；本地Qwen仍作为历史与可切换对照。** 正式诊断模型的准入仍需第5节的扩大评测。
